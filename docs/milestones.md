# マイルストーン

実行する前に、何が起きるか予測する。外れたらそこを調べる。

## Stage 0 — 動かす

- [x] host から guest を呼んで、文字列が出力される

わかったこと:
- 非決定性の入り口はコードを読んだだけでは分からない
    - 何を記録・制御すべきかは、ソースコードではなくビルド後のコンポーネントのimport一覧である

## Stage 1 — 乱数を入れる

- [x] guest で `wasi:random` を使う
- [x] 2回実行して出力が変わることを確認

わかったこと:
- WITに`import wasi:random/...`を1行足すだけで非決定性が入り込む
- コンポーネントのimport一覧には、意図して足したものとstdが自動で持ち込んだものがフラットに並ぶ
- importされていても、実際に呼ばれなければ出力には影響しない

## Stage 2 — 差し替える

- [x] host 側で `wasi:random` を固定値を返す実装に置き換える
- [x] 何度実行しても同じ出力になることを確認

わかったこと:
- guest側のコードを一切変更することなく、host側の設定だけで非決定性の入り口を完全に掌握できる
- guestには渡された値が本物の乱数か固定値かを検知する手段がない
- Linkerへの二重登録による上書きはできないため、後から上書きする方針は使えない

## Stage 3 — 記録と再生

- [x] 記録: 本物の乱数を返しつつ、値をファイルに書く
- [x] 再生: ファイルから読んだ値を返す
- [x] 記録時と再生時で出力が一致することを確認

わかったこと:
- 非決定性の入り口を握れば、ゲストを無改造のままホスト側だけで記録・再生が完結する
- 呼び出し順序はログの行順で表現できるため、記録対象は値だけで成立する
- u32やfill_bytesを内部的にu64に統一することで、記録対象を1種類に絞れた
- 記録した実行ログさえあれば、一回きりの実行コンテキストを何度でも決定論的に再現できる

## Stage 4 — 壊す

- [x] ログの値を書き換える → 予測: その値がそのまま出る → 的中
- [x] ログから1行削る → 予測: 実行時 panic → 的中（範囲外アクセス）
- [x] 記録時と再生時で guest のコードを変える → 予測: 気づかず成功する → 的中
- [ ] ログの順番を入れ替える → 実験1と同じことしか分からないので省略

わかったこと:
- ホストはログの数値を疑わずに順番に渡すだけ（書き換えたらそのまま出た）
- ゲスト側はそれが本物の乱数かログの値か見分けがつかない
- 要求が多すぎる（ログ不足）とpanicで落ちるが、要求が少ない（ログ余り）と正常終了して素通りしてしまう
- 再現がズレているのに成功したように見えるのを防ぐため、ログの消費数をカウントして警告する仕組みが必要だった

## Stage 5 — 時刻

- [x] `wasi:clocks/wall-clock` を記録・再生する
- [x] 乱数と時刻を1本の台帳にまとめ、種類も記録する
- [x] guest の呼び出し順を変えて、順序のズレが検知されることを確認

わかったこと:
- 時計のトレイトは`&self`だったので、`Mutex`が必要だった
- 実時刻を再生すると、guestから見える世界は記録した瞬間で止まる
